# Questions for OpenZMS: burst annotations and sensor-set observation ids

From RFObserver, 2026-10-20. Context: RFObserver will send every burst it detects (time,
frequency, power, SNR, and its rtl_433 attribution) as an annotation on the averaged
observation of the window it started in, in batches of 20 or every 0.5 s, whichever comes
first. Design: `docs/superpowers/specs/2026-10-20-zms-burst-annotations-design.md`.

What we see in zms-dst today (main, 2026-09-25): annotations can be created only through the
southbound gRPC `CreateAnnotations` (batch, no auth); the observation must already exist and
one unknown observation fails the whole batch; annotations cannot be updated; a client
observation id is accepted only with `X-Api-Observation-Path` (direct writes).

## Annotation batch API

1. **Transport and auth.** Will the batched annotation API be HTTP on the DST (like
   `POST /observations`, with `X-Api-Token` and `X-Api-Monitor-Id`), or the existing gRPC
   `CreateAnnotations`? If gRPC, how is it authenticated, and where do we get the `.proto`?
2. **Path and payload.** Route, content type, and the request and response shapes, with an
   example. Per item: `observation_id`, `type`, `name`, `description`, `value`, `min_freq`,
   `max_freq`, `sample_start`, `sample_count`; anything else?
3. **creator_id.** Taken from the token, or supplied by us? If by us, which id (monitor id)?
4. **Partial failure.** Today one unknown `observation_id` rolls back the whole batch. Could a
   batch return per-item results instead, so one bad item does not drop the other 19?
5. **Limits.** Maximum items and bytes per batch, and any rate limit per monitor.
6. **Volume.** One HCRO sensor logs about 568k bursts a day (~6.6/s average, bursty), so up
   to ~570k annotation rows per sensor per day, also published to Iceberg. Is that
   acceptable, or should we send only bursts above an SNR floor, or summarise?
7. **Time.** Annotations have no time columns; we will put the burst's start and stop
   (UTC, ISO 8601) in `value`. Would you rather have `starts_at` / `ends_at` columns, or use
   `sample_start` / `sample_count` against the observation? (Our observations carry an
   averaged PSD, not IQ samples, so sample offsets do not map naturally.)
8. **Type and name.** We plan `type: "rfobs-burst"`, `name`: the rtl_433 model when decoded,
   else `"burst"`, and `value.schema: "rfobs-burst/v1"`. Any naming convention to follow?
9. **Updates.** We send each burst once, when its attribution is final (up to 10 s after
   detection). Confirm annotations stay immutable, or tell us if an update call is planned.

## Sensor-set observation UUID

10. **How to send it.** Header (as `X-Api-Observation-Id` today, without the path
    requirement) or a field in the SigMF metadata? For `application/sigmf-archive` uploads.
11. **Format and uniqueness.** UUIDv4 generated by the sensor; what happens on a collision or
    a reused id?
12. **Idempotent resubmit.** If we resubmit an observation with the same UUID (after a
    timeout where we did not see the response), would you return the existing observation
    (`200`) rather than create a duplicate or error? That would let us retry observations and
    still attach their annotations.
13. **Ordering.** With a sensor-set UUID, may annotations be posted before the observation
    has been created (for example, held server-side until it arrives), or must the
    observation exist first, as today?
14. **Timeline.** When are the batch API and the sensor UUID expected, and on which
    environment can we test (DST URL)?

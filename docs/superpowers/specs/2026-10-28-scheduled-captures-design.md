# Scheduled IQ captures (ms-timed)

Date: 2026-10-28. Status: design, approved for planning once reviewed.

## Intent

Several sensors record the same instant, so their IQ files can be lined up
afterwards (for example one transmission seen from several sites). A user or a
script sets a window (start to the millisecond, duration) once, either on one
sensor or through the fleet on several, and every chosen sensor writes a file
that starts at that instant on its own clock, cut to the sample.

Accuracy across sites is bounded by the sensors' clocks, which today are NTP
(systemd-timesyncd, public pool: a few ms, see
`docs/debugging/2026-10-28_hcro-time-sync-ptp.md`). PTP from the White Rabbit
gear, and later PPS/10 MHz into the radios, will improve that without changing
this design. Every file says which clock it was cut on so the alignment error
is known afterwards.

## Goals

- Schedule one-off windows and repeating windows, each with a start time in
  UTC to the millisecond and a duration.
- The file starts at the sample nearest the requested start on the sensor's
  host clock (the existing per-chunk capture time, `capture/clock.py`) and
  holds exactly `duration x sample rate` samples: lost samples are zero-filled
  and listed in the metadata gaps, never hidden. Only a retune ends a file early
  (status `partial`).
- Set, list and delete schedules from the sensor's Captures page, the sensor
  API, the Fleet Captures page and a fleet API. A fleet schedule has one ID on
  every sensor it was sent to.
- A scheduled window records even when another capture (manual, armed power
  trigger, another schedule) is in progress: it is its own file, written in
  parallel.
- Collection statistics count scheduled captures as their own category.

## Non-goals

- Changing SDR parameters. A scheduled capture records whatever the radio is
  tuned to at that moment (frequency, rate, gain unchanged). Tuning per schedule
  is a later feature; the schema should not block it, nothing more.
- Clock discipline (PTP, chrony, PPS). Separate work.
- Recording windows late. A window whose start passed while the sensor could
  not record is marked missed, not recorded afterwards.
- Backfilling or editing schedules in place (delete and re-create instead).

## Anti-goals

- A scheduled file that is silently shorter, shifted, or missing samples.
  Every deviation (late start beyond the ring, dropped chunks, overflows) is in
  the file's metadata and the run's status.
- A scheduled capture that disturbs an ongoing manual or triggered capture
  (stops it, truncates it, changes its file).
- Ambiguous time: everything in the API and the UI is UTC.

## Decisions made with the user

- Use case: same instant on many sensors.
- Schedule shapes: one-off and repeating.
- Set from both the per-sensor UI/API and the fleet.
- Overlap with another capture: the scheduled window records too, in parallel.
- Clock: NTP for now; PTP over LAN later when the WR master is configured;
  PPS/10 MHz later still.
- Storage: scheduled captures are saved in `manual/` (never evicted by the cap),
  with origin shown as "scheduled".
- Collection statistics: their own category (`scheduled_captures`,
  `scheduled_bytes`, `scheduled_seconds`), included in the totals.
- Lost samples (USB overflow, dropped chunks, writer behind) are zero-filled in
  scheduled files, so sample index always equals time from the requested start
  and files from different sensors line up by index. Every filled stretch is
  still listed in the metadata gaps (index, count). This differs on purpose
  from manual/trigger captures, which stay contiguous and unfilled.
- A retune or reconfiguration during a window (sweep step, config change) ends
  the file at the retune; the run is `partial` with reason `retuned`. Creating
  a schedule on a sensor in sweep mode (FREQUENCY_STEP > 0) is allowed but the
  UI and the API response warn that windows longer than the dwell will be cut.
- UI time: entered and shown in UTC, with the sensor's local time shown beside
  it for convenience (its zone from its location, as in the collection API).

## Behaviour

### Schedule

Fields:

- `id`: string. Generated by the sensor for a direct API call, or by the fleet
  for a fleet schedule (same id sent to every sensor). Client may supply it
  (idempotent create: the same id and body again is a no-op, a different body
  is 409).
- `start`: UTC instant with ms resolution. API accepts ISO 8601 with a `Z` or
  offset, or `start_ms` (Unix epoch ms). Stored as integer epoch ms.
- `duration_ms`: integer, > 0.
- Repeat (optional): `every_ms` (> `duration_ms`, so runs of one schedule never
  overlap) and either `count` (total runs) or `until` (UTC, last run must start
  before it). Run k starts at `start + k x every_ms`: the same instants on every
  sensor, regardless of when each sensor received the schedule.
- `label`: optional free text, shown in the UI and written into file metadata.
- Created time and source (`api`, `ui`, `fleet`).

Validation (400 with a detail): start more than RING seconds in the past (see
below); duration above a maximum (builder's call; suggested 600 s); `every_ms <=
duration_ms`; neither or both of `count`/`until`; a schedule whose total bytes
(runs x duration x rate x 4) exceed free space above the storage floor (409,
same refusal wording style as recording refusals).

Schedules persist in the sensor database and survive restarts. Deleting a
schedule cancels its future runs; a run already recording finishes (builder's
call whether delete also offers "stop now"; default: finishes).

### Runs

Each run has a status: `pending`, `recording`, `recorded`, `missed` (could not
start: sensor down, pipeline stopped, replay active, storage refused), and
`partial` (recorded with dropped samples or a late start; counts in metadata).
Recorded and partial runs link to their capture file. Run history is kept for
past runs (builder's call on retention; suggested: the newest 500 runs per
schedule).

### Cutting to the sample

The receiver thread already knows each chunk's first-sample host time and its
stream position (`_ChunkTimes`, the pre-trigger ring with `total_written`). The
ring holds the last 1 to 2 s (TRIGGER_PRE_SEC, longer with isolation). So:

- A window may start up to about one ring length in the past when it reaches the
  sensor (fleet fan-out delays); the start is then taken from the ring.
- Otherwise the run starts when the chunk containing `start` arrives: the file
  begins at sample `floor((start - chunk_time) x rate)` into that chunk and ends
  after exactly `duration x rate` samples.
- The mapping uses the same host-clock estimate the rest of the pipeline uses
  (`CaptureClock`), so scheduled files agree with burst times and live
  timestamps.

### Writing in parallel

The scheduled capture is independent of the existing single recording state
machine in `StreamingProcessor` (manual/trigger). It gets its own writer
(queue plus thread, like the disk-streaming recorder) fed from the receiver
thread, so a manual or triggered capture and a scheduled one can write at the
same time. At 26 MS/s each stream is about 104 MB/s; if the writer falls behind,
chunks are dropped and recorded as gaps (status `partial`), never blocking the
receiver thread; the dropped stretch is written as zeros (from the writer
thread, so the receiver thread does no extra work) and listed as a gap. Two scheduled runs from different schedules may overlap; the
builder decides whether that is one writer per run or one shared writer (a
reasonable limit, e.g. 2 concurrent scheduled runs, is acceptable with the
excess runs marked missed).

### Files and metadata

- Saved in `manual/` with the usual name scheme plus a marker that it is
  scheduled (builder's call, e.g. `...-sched.sc16`), with the same companions
  as a manual capture (SigMF meta, PSD grid so the waterfall and detections
  views work; the grid may be computed after the run if computing it live is
  too costly).
- The captures list shows origin "scheduled" and the schedule label.
- Metadata (SigMF `rfobs:` extension, alongside the existing keys):
  `schedule_id`, `run` (k), `requested_start` (UTC, ms), `first_sample_time`
  (UTC, ns precision as computed), `start_error_ns` (first sample minus
  requested), `clock_source` (`ntp` now; later `ptp`, `pps`), `clock_server`
  and `clock_offset_estimate` if they can be read cheaply (timesyncd/chrony),
  sample count, gaps, label. Files from different sensors for the same run share
  `schedule_id` and `run`.

### Collection statistics

`collection_hours` gains `scheduled_captures`, `scheduled_bytes`,
`scheduled_seconds` (migration adds columns with 0). All `/api/collection/*`
responses include them and the totals include them. `docs/collection-api.md`
and its doc test are updated.

## API (sensor)

Under `/api/schedules` (no auth, like the rest of the sensor API):

- `POST /api/schedules`: create (body as above). 201 with the schedule and its
  next runs.
- `GET /api/schedules`: active and finished schedules with next run time.
- `GET /api/schedules/{id}`: one schedule with its runs.
- `DELETE /api/schedules/{id}`: cancel future runs.
- Errors as 400/404/409 with `detail`, like the collection API.

A doc page `docs/schedules-api.md`, linked from the README, tested the same way
as `docs/collection-api.md` (examples executed by the test suite).

## API (fleet)

- `POST /fleet/api/schedules` with the schedule body plus `sensors: [ids]`:
  generates one id, sends the create to each sensor in parallel, returns the
  per-sensor result (created / error with detail). Partial success is allowed
  and reported; the UI shows which sensors failed.
- `GET /fleet/api/schedules`: merged list from all sensors, grouped by id, with
  each sensor's status.
- `DELETE /fleet/api/schedules/{id}`: deletes on every sensor that has it.

## UI

Captures page (sensor), a Schedule card at the top, Apple-style like the rest:

```
Schedule a capture
  Start (UTC)  [2026-10-28] [18:30:00.250]
  Duration    [2.000] s
  Repeat      [ ] every [60] s  until [....] or [10] times
  Label       [..........]
                                   [Schedule]

Upcoming
  18:30:00.250 UTC (11:30:00.250 PDT)  2.000 s  every 60 s (3 of 10)  in 00:04:12   [Delete]

Recent runs
  18:29:00.250  recorded  <file link>  52 MB
```

- All times entered in UTC, ms shown. Beside the form, a live clock shows "now"
  in UTC and in the sensor's local time (zone name, e.g. America/Los_Angeles,
  the same zone the collection API resolves). Upcoming windows and recent runs
  show the sensor's local time next to UTC (e.g. `18:30:00.250 UTC (11:30:00.250
  PDT)`). Entry stays UTC only. On the fleet page each sensor's row uses that
  sensor's zone.
- Fleet Captures page: same card with a sensor picker (all selected by default);
  upcoming and recent runs show per-sensor status.
- Scheduled captures appear in the normal captures list with a "scheduled"
  chip and their label; clicking opens the usual detail/waterfall.
- Pages must work offline (no CDN), no emojis, no em-dashes in UI text.

## Constraints

- Python >= 3.10 (Jetsons run 3.10), no new heavy dependencies.
- Receiver thread must never block on scheduling or writing.
- Existing manual/trigger recording behaviour and files unchanged.
- Tests: unit tests for the scheduling math (run instants, sample cut), the
  API, persistence across restart, missed runs, parallel recording with a
  manual capture (mock receiver), stats category; integration test end to end
  with the mock receiver.

## Left to the builder

Max duration and concurrency limits, run-history retention, writer structure,
PSD grid live vs after the run, file name marker, where the scheduler lives
(a component the receiver thread consults per chunk is the natural fit),
whether delete can stop a running run.
